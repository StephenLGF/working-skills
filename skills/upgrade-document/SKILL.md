# 升级文档

## 能力与适用环境

本 Skill 是可移植的工作说明，不依赖 Codex 的专有 API、文件目录、模型或浏览器插件。支持读取 Markdown 指令并使用终端的助手可直接使用；不支持 Skill 自动加载的助手，可将本文件作为任务说明，再按需提供引用文件。

推荐具备 Git、本地 `gitee` CLI、本地 `lark-cli`，以及对应仓库、番茄和飞书的读取权限。使用者自行完成安装和账号配置；不要使用作者机器的路径、profile、租户、凭证。已配置的 MCP/连接器可作为读取能力的替代，不是必需依赖。首次使用或 CLI 不熟悉时读 [references/tools.md](references/tools.md)。

本流程只整理文档，不自动打包、部署、执行迁移、修改应用配置、流转卡片、评论 PR 或发送消息。预览确认与飞书写入是两个阶段；“看看”“整理草稿”只授权本地预览。

## 用户入口与信息补齐

可接受：

- 完整 PR 链接，或当前仓库明确时的 `!2087` / “PR 2087”。
- 用户明确指定的基准 tag/commit/分支与目标分支/commit。
- 多个应用的 PR、仓库与分支范围，汇总为同一期升级文档。
- 已有飞书文档链接，要求更新预览；或升级日期和上期模板，要求新建预览。

输入优先级：当次明确要求 > 会话中已确认范围 > PR 元数据 > 可验证的仓库上下文。仅有数字且仓库不明时询问仓库，不能猜编号归属。仅有 PR 时，如果当前会话明确了升级文档则沿用；否则可先根据 PR 整理已知变更，询问升级日期和模板位置。不要为无关的缺失字段阻塞可以完成的部分。

先读取仓库要求的 AI 文档，按路由选择相关业务说明。不要无差别加载整套仓库文档。

## 每次读取最新内容并固定本轮证据

1. 重新读取 PR 的源/目标仓库、分支、状态、最新 diff refs；不能只复用旧草稿或之前查询结果。
2. 对涉及的远端分支执行 fetch，再解析成完整 SHA。远端分支被删除或 fetch 失败时明确说明，不能声称“最新”；不要 checkout、reset、merge 或修改用户工作树。未提交改动不属于升级范围。
3. 重新读取相关飞书文档及本轮相关番茄卡片。一次运行内可缓存同一卡片，避免重复请求；下一次整理必须刷新。
4. 记录读取时间、各仓库基准/目标 SHA、merge-base、PR 状态及文档 revision，供核验使用。证据不写入预览正文。
5. 如果整理期间 PR 分支头发生变化，重新 fetch 并补查增量；遇到持续更新不能无界重试，交付最后一次完整核验的快照，并在回复注明时间及新变化。不要将 PR 的模拟合并 SHA 当作源分支头。

### 比较口径

| 场景 | 候选提交 | 代码核验 |
|---|---|---|
| 未合并 PR | 目标最新 `BASE..TARGET` 源最新 | merge-base 到源最新的 PR 差异 |
| 明确基准且是目标祖先 | `BASE..TARGET` | `git diff BASE TARGET` |
| 明确基准但两端分叉 | 先说明分叉并确认净差异或 PR 口径 | 不静默替换为 merge-base |
| 已合并 PR | 使用该 PR 合并时的源头、基准、diff 或合并提交证据 | 不以现在两端相同认定“无升级” |
| fork PR | 分别获取源仓库和目标仓库的正确引用 | 不把同名本地分支当作源分支 |

PR 作为本次范围时，允许采用 PR 比较口径，不额外询问分叉；记录两端及 merge-base。不把主线独有变化描述成本次删除。`main/master` 或远端默认分支不一定是业务主线，以 PR 目标或用户明确指定为准。

## 整理需求与 Bug

先从范围内 commit 的完整 subject/body、合并或 squash 提交、PR 关联信息提取卡片编号。不要只读取第一行，squash 提交可能包含多张卡片。提交历史提供候选，实际代码差异核验交付效果；完全回退的变化不列为已交付。纯合并记录、重复说明、测试/格式调整和开发工具命令不单独列为业务功能，除非影响交付。

随后用番茄/Gitee Team 的卡片详情、类型元数据及层级分类；Gitee Code Issue 不能替代番茄卡片。

- Story、EnablerStory 等实际需求类型进入需求表；Bug、测试缺陷等实际缺陷类型进入缺陷分类流程。工作空间的类型 key/name 可定制，按元数据识别，不根据卡片编号前缀或 commit `feat/fix` 猜测。未知类型在回复询问。
- Bug 位于 Story 或已识别需求类型的后代层级：归入对应需求，不在 Bugfix 重复展示。需要读取最近的需求祖先；仅普通“关联”而非父子层级不能省略。不要误把批次、Epic 等容器作为具体需求。
- 本次只有需求子 Bug 的提交时，需求表说明本次修复或完善的部分，不把整个历史需求描述为首次上线。
- 独立 Bug 按卡片去重。同一卡片多个提交、多个 PR 汇总成一条；同一 PR 多个独立 Bug 分别保留。跨应用同一卡片可按应用分别描述真实影响。
- PR 或 commit 中没有卡片的实际变更、层级缺失、卡片无权限或类型未知：保留证据并在聊天回复列出，不编造卡片、不静默丢弃、不强行分类。
- 负责人和 QA 从卡片实际字段及字段元数据读取，不能用提交作者或 PR 作者替代。字段缺失则正文留空，在回复说明。

### 说明文案

文案由 AI 根据卡片问题、提交记录和实际代码差异整理，不要求照抄标题或 commit。以一句话表达用户可感知的需求或修复。只描述对应卡片的变化，不混入同一 PR 里其他卡片的效果；不把卡片提出的所有问题当作代码均已修复。

正文只展示做了什么需求、修了什么 Bug，保留卡片编号和链接，不展示 PR/commit 编号、数量、映射或开发过程。Bugfix 格式为 `- [卡片编号](真实卡片链接) 修复说明。`，各条连续排列，不插入多余空行。需求表后不附“相关 PR”映射或重复功能说明。

交付回复统一说明“说明文案由 AI 根据卡片和代码变化整理”，不在正文逐条加 AI 标记。分类与边界例子见 [references/cases.md](references/cases.md)。

## 核验测试与完成状态

每次整理必须重新读取本轮每张需求和 Bug 的当前持久化状态，包括归入需求而不单列的子 Bug、仅为子 Bug 引入的父需求，以及更新预览中保留的原文事项。记录卡片编号、实际状态名称、状态类型、读取时间和判定依据；不只检查最终正文的独立条目。

- 区分“测试已通过”“流程已完成”“尚未通过/完成”和“无法核验”。只有工作空间元数据、工作流语义或用户明确规则支持时，才能把状态归为通过或完成。
- 常见“测试通过”“测试完成”“已完成”“完成”可作为查询候选，但不同空间命名不同，按实际流程核实。`Finished` 类型可证明流程终态，但不能单独证明测试通过；“已关闭”“已解决”可能有重复、拒绝、取消等语义，不能一律当测试通过。
- “待测试”“测试中”“待开发”“开发中”“重新打开”不能报告为已通过或已完成。“修复完成”若实际流向待测试，只说明开发修复完成，不说明测试通过。
- 需求完成不能替代子 Bug 核验；需求已完成但某子 Bug 未通过/完成，仍须指出。Bug 已通过也不能自动认定其父需求全部完成。
- 合入 PR、集成 ✅、有包版本、提交作者说明、历史测试报告均不能替代本轮卡片状态读取。卡片完成也不等于本次具体包已经测试通过。
- 不通过、含义不明或读取失败时，继续生成可完成的预览；不擅自删除该事项、改状态或在正文新增待确认/警告列。仅在聊天回复逐项列出卡片链接、当前状态及原因。全部满足时简要报告核验结果，并区分完成与测试通过，不宣称没有证据的测试结论。
- 用户未指定过滤策略时不自动排除未完成项。用户若要求“只列已测试通过的”，按已确认状态语义过滤，并在回复说明排除项。

## 检查配置与现场操作

检查差异中所有新增、修改、删除、重命名的 `.yml` / `.yaml`，按需追踪环境变量、manifest、插件依赖、默认值、初始化、脚本和迁移代码。配置可能存在其他文件，因此无 YAML 变化不能直接推断无现场操作。

对每项实际需要的动作记录：应用/环境、配置位置、所需值、操作顺序、依赖、必要的备份和核验方式。升级前必须完成的放前置；依赖新版本才能执行的放后置。顺序或值不确定时在回复询问，预览不写猜测操作。

配置参数、内部代码开关、API 参数、开发 tunnel 命令不自动等于现场环境变量。敏感值用占位符，不读取或传播真实秘密。迁移脚本只说明来源、用途和已知执行要求，不执行。不自动继承上期一次性操作。

完整检查后未发现新增操作可写“本次无新增前置操作/后置操作”；范围缺失或未核查则保持空白，不能写“无”。

## 生成可直接阅读的预览

更新以目标文档结构为准；新建以最近一期文档作模板。没有可读模板时使用 [references/preview.md](references/preview.md)。保持已有应用分类和有效字段。历史文档仅是结构及版本基线，不把其中的人名、版本和升级内容当作默认值。

- 预览按正式文档排版，不含“待确认”“待补充”“待最终打包”、核验清单、来源 revision 或生成过程。未知字段留空，疑问和证据放聊天回复。
- 本地输出路径优先遵从用户要求，否则使用宿主可写的工作产物目录；不用作者个人绝对路径，不必依赖 Codex 打开面板。可用宿主的 Markdown 预览或交付链接。路径中有空格时正确引用。
- 新建不继承历史需求/Bugfix/一次性操作；继承插件应用清单和各环境版本。更新时保留其他人及未涉及部分。原文事项不在本 PR 范围时，先保留并在回复说明，不静默删除。
- 只有必要升级的应用才更新版本。最终包未指定时，预览暂保留原有版本和附件，回复明确它们未最终确定；新建时可继承上期版本表，但不复制上期附件当作本期交付包。缺少镜像、下载和测试报告来源时留空，不生成虚假链接或结论。
- ✅ 表示已合并到集成环境，不代表已部署或已测试。通常已集成；用户确认或有集成分支证据时填写，无需逐条确认。仅主线证据不能自动证明集成。原有标记保留；PR 本身未合入主线与内容已在集成环境并不矛盾。
- 插件各环境列的原有标记保留；其含义未明确时不新增，不套用需求集成语义。

预览交付前检查：需求和所有相关 Bug 状态已核验、卡片链接真实、归类依据可核验、子 Bug 未重复、说明没有跨卡片混写、未知字段未猜测、已有内容未丢失、正文无过程说明、列表无多余空行。回复提供预览、AI 文案来源说明及少量需要用户决定的事项；不要默认展示大量 SHA/提交统计。

## 最终版本与飞书写入

版本和附件最后填写。用户可能多次打包同名或不同版本的包；不要按最高版本号、mtime、文件名或“最新出现”自动决定最终包。用户提供或选择后，核对可用的包内版本元数据、文件名、应用及指定环境列；冲突在回复确认，不批量覆盖全部环境。

用户仅确认预览时保持本地；明确要求“写入/更新飞书”后才操作。写前重新读取相关段落与 revision，处理别人新增内容；优先块级/段落修改，不整篇 Markdown overwrite 导致附件、表格、@用户和其他应用丢失。新建需明确目标 Wiki/目录，避免同名重复创建。

按本地 CLI 帮助及格式指南创建/更新/插入附件；MCP 可用时也遵守同一范围。写后重新读取验证正文、去重和版本/附件，再给文档链接。失败说明已成功和失败的具体部分，保留预览，不无界重试、不重复上传或创建。

共享 Skill 仅包含规则和通用示例，不打包运行时草稿、原始卡片正文、签名下载地址、用户标识、登录信息或凭证。`agents/openai.yaml` 仅为 Codex 可选界面元数据，其他宿主可忽略。
