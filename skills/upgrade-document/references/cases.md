# 分类和异常处理示例

以下卡片和 PR 编号仅为虚构例子，不代表默认项目。用于判定规则，不用于复制正文。

| 输入情况 | 处理结果 |
|---|---|
| 一个 squash commit 含 Story S-10 和子 Bug B-11/B-12 | 读取三张卡片；确认层级后需求表一行，Bugfix 不再列两条子 Bug |
| 本期仅修复历史 Story 的子 Bug | 需求行描述本期修复部分，不写整个历史功能首次上线 |
| B-20 只“关联”S-10，无父子层级 | 不能仅因关联省略；另有本期引入的明确因果证据则归入需求 |
| B-21 的父项是 Task，祖父是 Story | 读取 Task/祖先类型，归入最近的需求 Story |
| B-22 的父项是批次/Epic | 不把批次当具体需求；继续确认祖先，无具体需求则保留独立 Bug |
| EnablerStory E-30 的标题包含“问题单” | 按实际需求类型放需求表，不因标题词语分到 Bugfix |
| 同一 PR 包含搜索错误修复和目录性能改进，属于不同卡片 | 分别写各卡片说明，不把两项效果拼到其中一张卡片 |
| 候选提交修改后又完全 revert | 排除已回退内容；部分保留时只描述实际保留效果 |
| 原文事项不在当前 PR 差异 | 更新时先保留，回复列出范围差异；新建时不从上期继承该事项 |
| 主线有某功能，但本 PR 没有新增 | 不因最终代码存在就声称此 PR 新增了它 |
| PR 草稿未合入主线，内容已在集成分支 | 集成证据充分则可标 ✅；不把 PR 草稿状态当作未集成 |
| 只有主线提交，没有集成证据 | 不自动新增 ✅，回复说明缺失集成证据 |
| YAML 未变，但代码增加部署所需变量 | 追踪变量用途，确认是否手工设置及默认值，再整理操作 |
| showAbnormalFolder 等请求参数新增 | 不是自动新增部署变量；仅对真实现场操作写配置 |
| 上期有一次性迁移 SQL | 新一期不自动复制；本期明确需要且有依据才写 |
| 表格版本 100、旧附件版本 102 | 保留预览现状，回复指出冲突；最终包选择前不替用户决定 |
| 用户两次上传同名 zip | 最终选择依据用户确认及包内元数据，不按名称/mtime 自动替换 |
| 用户说“草稿可以” | 不写飞书；用户明确要求写入后再操作 |
| 飞书 revision 更新，其他人补了 Team 内容 | 重新读取、保留新增段落，只修改确认范围 |
| fetch 或卡片权限失败 | 继续可完成内容，回复列出具体未核验范围；不称完整/最新 |
| 已合并 PR 两端无差异 | 读取合并时证据，不生成“没有改动”的错误结论 |

状态核验例子：

| 状态情况 | 处理 |
|---|---|
| Story 测试完成，子 Bug 仍待测试 | 回复列出子 Bug，不以父级状态替代 |
| Finished + 取消/拒绝/重复 | 按工作流终态语义报告，不称测试通过 |
| 修复完成但下一状态是待测试 | 视为尚未测试通过 |
| 卡片测试完成，最终包尚未选择 | 可报告卡片状态，不宣称最终包测试通过 |
| 卡片无权限或状态字段缺失 | 回复标记无法核验，预览不加警告列 |

核验能力缺失时不编造数据。普通缺少最终包、镜像或报告不阻塞已知需求/Bug 预览。范围无法判定则停止范围相关分析，并准确询问缺少的信息。

公共位置归因例子：

| 情况 | 处理 |
|---|---|
| 本期需求修改共享接口的返回结构，旧页面据此报错，修复补兼容 | 引入提交、调用链和修复明确时并入本期需求 |
| 本期配置默认值调整导致另一模块失效 | 变量用途及前后行为证据充分时并入对应需求 |
| 相同组件被本期改过，但 Bug 来自未改动的历史分支 | 不因组件重合而省略，保留独立历史 Bug |
| 上次实际交付已存在的缺陷挂在旧 Story 下 | 历史 Bug 单列，父子层级不能掩盖历史交付问题 |
| 公共改动可证实导致 Bug，但归属多个需求不明确 | 回复询问归属，不能随意挑需求或静默删除 |
